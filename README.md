# AE352 Team 15 - three-mission simulation

## Start here in VS Code / Windows

1. Extract this folder inside your existing `AE352_Drone` workspace.
2. Open a terminal in the extracted folder (the folder containing `run_missions.py`).
3. Select the existing `.venv` interpreter in VS Code. If the environment is activated:

```powershell
python -m pip install -r requirements.txt
python run_missions.py
```

If you extracted this folder as `project/AE352_drone_missions/drone_missions` and have NOT activated
`project/.venv`, use these commands from inside `drone_missions`:

```powershell
..\..\.venv\Scripts\python.exe -m pip install -r requirements.txt
..\..\.venv\Scripts\python.exe run_missions.py
```

It simulates all three missions, prints their status, and saves **actual figures and data**
in `outputs`. It intentionally does not open pop-up plot windows. Open the PNGs in VS Code,
or `outputs/figures/all_mission_figures.pdf` to browse every figure.

For the optional numerical sensitivity check, run `python validate.py` (or the same
explicit environment path). It reruns the missions with half the time step and writes
`outputs/validation.json`. Runtime depends on your computer; allow a few minutes.

For a standalone equilibrium check: `python drone_dynamics.py`.

## Files and responsibilities

- `drone_dynamics.py`: 16-state function and hover test using parameters.py.
- `parameters.py`: editable parameter dictionary, controller gains and limits.
- `missions.py`: desired position/velocity/acceleration/yaw trajectories.
- `controller.py`: feedback, allocation and motor-torque commands.
- `simulation.py`: zero-order-held torque inputs, RK4, ground constraint, energy.
- `metrics.py`: measured requirement checks with explicitly documented tolerances.
- `plotting.py`: report figures (generated by Matplotlib, not fabricated trajectories).
- `run_missions.py`: one-command full run and exports.
- `validate.py`: vector-form checks and time-step/controller-sampling refinement.
- `outputs/*.csv`: full-rate histories, SI units stated in column names.
- `outputs/*.npz`: compact NumPy copies; actual states in `s`, references in `ref`.
- `outputs/metrics.json`, `RESULTS.md`: measured results and individual checks.
- `outputs/parameters_used.json`: exact parameters used for that run.

CSV state order is x,y,z,vx,vy,vz,phi,theta,psi,p,q,r,Omega1,...,Omega4.
Motor torques are in N m. Angles and angular speeds use radians and rad/s internally.
Plots convert Euler angles to degrees and rotor speeds to rpm where labeled.

## Mission initial conditions and schedule

1. **Hover (120 s):** position (0,0,1) m, zero velocity/attitude/body rates,
   identical hover rotor speeds. Exact equilibrium under feedback, no perturbation.
   This is not evidence of disturbance rejection.
2. **Circle (70 s total):** start at (2,0,1) m, at rest, level, hover rotor speeds.
   Increase angular speed smoothly from 0 to 0.25 rad/s over 5 s while staying on
   the radius-2 m reference circle. Score t=10 to 70 s: a full 60 s at 0.5 m/s.
   Yaw reference is held at zero; pointing tangentially is not a requirement.
   Startup energy is included.
3. **Sequence (163 s):** start on the ideal ground plane at (0,0,0), all rates and
   rotor speeds zero. Hold to 1 s; smooth takeoff 1-5 s; hover 5-8 s; first straight
   leg 8-13 s from (0,0,1) to (5,0,1); stop 13-16 s; yaw left 16-20 s to +90 deg;
   hover to 23 s; second leg 23-28 s to (5,5,1); stop 28-31 s; descend from 31 s.
   Both legs have a smooth quintic reference, covering 5 m in 5 s. Their speed is
   not constant: the required 1 m/s is an average. We measure actual integrated
   horizontal speed over each scheduled leg and separately check displacement,
   straightness, altitude, and stop speed. Do not substitute reference speed for
   actual speed in the report.
   Landing ramps over 2 s to 0.008 m/s, leaving margin below the hard 0.01 m/s limit.
   Touchdown is near 157 s with the default parameters; motors then disarm.

The descent position reference continues slightly below the ground until contact,
so tracking does not approach the ground asymptotically. The contact handler uses
an interpolated crossing time and records impact velocity BEFORE resetting velocity.
After touchdown the vehicle is held at rest and rotors coast down. The sequence
continues to 163 s; this post-touchdown energy is included. Raw reference CSV values
may be negative after touchdown; they are inactive because the controller is disarmed.

## Model and controller

The flight ODE matches the report's Eqs. (3)-(17), including its **quasi-steady yaw**
approximation. It has 16 states, with motor torque as the only in-flight actuation.
Body axes are forward-left-up; inertial Z is up; rotor 1 left, 2 front, 3 right,
4 rear. Spins 1/3 CCW, 2/4 CW from above. We do not add transient motor-reaction
yaw terms or gyroscopic effects that the report neglects.

Position feedback requests acceleration:
`a_cmd = a_ref + Kp*(position_ref-position) + Kd*(velocity_ref-velocity)`.
Desired total force is `m*(a_cmd + [0,0,g])`. Its direction and desired yaw define
a desired rotation matrix. A rotation-matrix attitude error and angular-rate
feedback request body torques. Reference angular-rate feedforward is obtained
by centered differences of nominal reference orientation (epsilon 0.001 s).
It does not read future actual states. Cross-product inertial coupling is compensated.

The allocation matrix maps squared rotor speeds to total thrust and body torques:

```
[ kT      kT       kT      kT   ]
[ L*kT     0      -L*kT     0   ]
[   0    -L*kT      0     L*kT  ]
[ -kQ      kQ      -kQ      kQ  ]
```

Solving this system gives speed commands, bounded between 0 and Omega_max.
Motor control is `M = kQ*Omega_actual**2 + Jr*(Omega_cmd-Omega_actual)/tau_motor`,
clipped to [0, M_max]. Actual rotor speeds still evolve through Eq. (16).
Zero motor torque permits aerodynamic deceleration; no regenerative braking is modeled.
Allocation clipping is a simple fallback, not an optimal constrained allocator.
Saturation counts are logged. Default runs have brief torque saturation at startup.

Torque inputs are held during each RK4 step; the controller updates at the step
rate (default 100 Hz). Reducing dt also increases the control-update rate, so
`validate.py` checks combined numerical/sampling sensitivity, not isolated RK4 order.
A changing controller sample rate is explicitly acknowledged in validation.json.

The ideal ground plane uses z=0 for the CoM and ignores landing-gear height. Before
liftoff, a normal reaction prevents downward motion. At touchdown velocities are
reset and the body is held at rest without bounce. We do not use the reset velocity
to claim a gentle landing. Contact is a simplifying addition outside the airborne ODE.

## Energy and interpretation

Electrical power is `sum(M_i*Omega_i)/(eta_m*eta_ESC) + P_aux`; integrate it using
the RK4 stage rotor speeds. All motor torques are nonnegative. During coast-down
stored rotor energy dissipates aerodynamically; it is not credited to the battery.
The selected battery is 4S, 14.8 V, 3.3 Ah (48.84 Wh nominal).
Usable energy is 140.7 kJ = 39.0833 Wh, rounded from 80% of nominal energy. The 80% usable factor
is not applied again as a discharge efficiency. Every mission starts with a fresh
battery. The sum is also reported but excludes connecting travel and is not a
continuous combined mission. Battery exhaustion aborts the run; no voltage sag,
current-dependent efficiency, thermal, motor electrical or capacity-fade model is used.

All three missions are ideal, deterministic simulations without wind, disturbances,
sensor noise or parameter uncertainty. Very small errors reflect this ideal model
and feedforward, not real flight accuracy. 

The project gives no tracking-error tolerances. For numerical checks we choose
2 cm position/radius/cross-track error, 0.02 m/s speed/stop tolerance, and 1 degree
yaw tolerance. These are explicitly OUR engineering tolerances, not instructor
requirements. Landing's 0.01 m/s bound is checked without relaxing it. Full measured
values are in metrics.json. If your team changes tolerances, retain the actual values.
